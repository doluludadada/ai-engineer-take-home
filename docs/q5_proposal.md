# 題 5｜公司規章問答助理提案

要做的事：員工直接用問的查請假、加班、報帳規定，助理照正式規章回答，並附上出處。

## 1. 開工前先問 HR 的 5 個問題

1. 正式的規章有哪些？放在哪？誰在更新？（先確定資料來源，只收正式文件）
2. 哪些文件不是所有人都能看？是照職級還是部門分？這個資料哪個系統查得到？（決定權限怎麼做）
3. 規章多久改一次？有沒有生效日？新舊版會不會同時有效？（決定版本怎麼管）
4. 哪些問題不要讓助理答、要轉給 HR？像薪資、申訴、個案。（決定範圍）
5. 員工現在最常問什麼？HR 能不能給標準答案，之後一起驗收？（測試題從這裡來）

問這 5 個，是因為這幾件事一開始沒問清楚，做到一半再改會很痛。我在美僑做內部系統時，也是先跟使用單位把這些談完才動工。

## 2. 第一版做什麼、不做什麼

做：只照已發布的規章回答，每個答案附出處（哪份文件、第幾條、哪一版）。找不到依據就說不知道，給 HR 窗口。用公司 SSO 登入。每個回答可以按「有幫助／沒幫助」。

不做：查個人資料，像「我還有幾天特休」，這要串 HR 系統，之後再評估。也不代送請假單，不做個案判斷和法律解釋。

## 3. 不同員工能看的規章不一樣

文件匯入時就標好誰能看，這個標記直接跟來源系統的權限，不另外維護一份。員工發問時，先用他的 SSO 身分篩出他能看的文件，再從裡面找答案，他不能看的內容不會送進模型。不能只靠 prompt 叫模型不要講，那個擋不住。上線前我會用一般員工的帳號去問主管限定的內容，確認問不出來。

## 4. 規章改版後不答舊內容

每份文件記版本和生效日。新版發布就重新匯入，舊版標成失效，找答案時只找有效的。答案上也顯示版本和生效日，員工自己看得出來。每次改版，把跟那份規章有關的測試題重跑一次。

## 5. 怎樣算可以上線、誰驗收

請 HR 出一批常見問題和標準答案，先抓 100 題，實際數量再跟 HR 談。權限測試只要有一題問出不該看的內容，就不上線。答對率和出處正確率的門檻跟 HR 一起訂。先給一個部門試用兩週。內容由 HR 的規章負責人驗收，權限和個資由資安或 IT 驗收，最後由主管決定上不上線。

補充：文件切段、轉向量、用相似度找段落這種做法，我還沒在正式專案做過。stock-agent 有用 ChromaDB，但我是用股票代號篩選，不是語意搜尋。所以我會先拿幾份規章做一個小的試，找得到對的段落再往下做。

## 過去參與的專案：美僑協會每月電子帳單系統

每個月把帳單用 email 寄給全部會員的系統。我在美僑協會任職期間（2025/03 到 2026/08）負責，工程師只有我一個。原本是外包廠商寫的，我用 FastAPI、Angular、PostgreSQL 重做，架構是 Clean Architecture。

| 部分                                                                                       | 我親手寫或我決定的                           | 其他人或廠商做的                       | AI 工具產出、我再修改的          |
| ------------------------------------------------------------------------------------------ | -------------------------------------------- | -------------------------------------- | -------------------------------- |
| domain 和 application 層（業務規則、寄送流程：寄前檢查、寄信、追蹤、中斷後接續、失敗重寄） | 全部                                         | 最早的版本是外包廠商寫的，我接手後重寫 |                                  |
| 寄信                                                                                       | 決定不用官方套件                             | 郵件服務是 Mandrill                    | 直接打 Mandrill API 的非同步程式 |
| 資料庫存取、API 層                                                                         |                                              | 帳單原始資料由 Oracle ERP 產出         | 大部分                           |
| 操作畫面（Angular）                                                                        | 畫面我先手繪在紙上；前端架構選 feature-based |                                        | 照我的草圖設計畫面、寫元件       |
| 測試、部署                                                                                 | 環境怎麼分是我定的                           |                                        | pytest、Docker compose 的 yaml   |

AI 工具用的是 Google AI Studio 和 ChatGPT。那時候是在網頁上問，把結果貼回來自己改，不是讓 AI 直接改整個專案。我另外寫了一個小腳本，可以快速複製我要的程式碼範圍貼給它。

domain 和 application 這兩層是我自己寫的。業務規則我先跟各部門確認過，再把規則抽成純函數。寄信的部分，我記得 Mandrill 官方的 Python 套件是同步的，所以沒用，改成直接打它的 API、用非同步送，比較快。

### 我親自排除過的問題

我接手後第一次跑每月寄送，寄到一半程式就停了，後面的會員都沒收到帳單。那時候還是外包廠商寫的版本。

我先看錯誤訊息和 log，是一個資料庫的例外。那段程式不是我寫的，我就把程式和錯誤訊息丟給 AI 分析，它列了幾個可能的原因，我再自己判斷是哪一個。最後確認是有一位會員的主要 email 和 cc 填的是同一個地址，程式沒處理這種情況，就整個崩潰。

當下我先把這一筆排除，讓它接著把剩下的寄完。後來重寫時，我把這類問題一次處理掉：寄之前先檢查資料，有問題的先挑出來；每一封信各自記狀態，中斷了可以從還沒寄的接著寄，失敗的可以單獨重寄。

之後中斷不用再手動處理，每次處理時間也從大約 3 小時降到 10 分鐘左右。

## AI 工具使用說明

- 提案：初稿用 Claude Code 產生，我再修改。先篩權限再找答案、文件記版本和生效日，這兩個做法是 AI 提的，我看過覺得合理就留著。
- 過去專案和排除的問題：都是我自己的經驗，AI 只幫忙整理文字。
