# 題 4｜評估：怎麼知道它夠好？

## 1. 選哪一個？還需要什麼資訊？

200 封換成封數來看：

| 指標           | chat-cheap | chat-default | 差幾封 |
| -------------- | ---------- | ------------ | ------ |
| 問題類別答對   | 182        | 188          | 6      |
| 訂單編號答對   | 194        | 196          | 2      |
| 捏造訂單編號   | 3          | 0            | 3      |
| 查核後還要重試 | 36         | 12           | 24     |

成本：chat-cheap 一封 1,900 × 1 = 1,900，chat-default 一封 1,300 × 8 = 10,400，default 大概貴 5.5 倍。

正確率我覺得兩個差不多，只差 2 封跟 6 封，換一批信可能就反過來。重試差比較多，36 對 12。我比較在意的是捏造的那 3 次。類別分錯頂多分到錯的組，訂單編號錯了，客服會去處理到別人的訂單。

現在就要上線的話我選 chat-default。但我不會只因為 3 比 0 就說 cheap 不能用。我會先把下面第 3 點的檢查做進去，再拿 cheap 重測，捏造的都擋得住的話，便宜 5 倍值得換。

還想知道的：

- 抽出來的結果是系統直接拿去用，還是客服看過才處理？
- 一個月大概幾封信？知道量才知道 5.5 倍是多少錢。
- 這 200 封是怎麼挑的？跟平常收到的信像不像？
- 裡面有幾封信本來就沒寫訂單編號？我猜捏造都出在這種信。
- 重試最多幾次？使用者要多等多久？

## 2. 200 筆夠不夠？「3 次 vs 0 次」說明什麼？

看比什麼。重試率 36 對 12 差很多，200 筆夠看。正確率不夠，200 封的 1% 才 2 封，多錯一兩封數字就變了。

3 比 0 只能說 cheap 真的會捏造，程式一定要擋。

不能說 default 就不會捏造，它只是這 200 封沒出現。假設它每 500 封捏造一次，200 封很可能剛好沒遇到。也不能說上線後就是這個比例，要看這 200 封跟實際的信像不像

我會再多收一些信，專挑容易出錯的：沒寫訂單編號的、有兩個編號的、信裡有電話或物流單號的。統計上到底要幾筆才夠我沒算過，要決定的時候我會去查，或問做過的同事。

## 3. 為什麼會捏造？程式裡還能做什麼？

模型是照前面的字去接看起來合理的字，它不會自己說不知道。如果輸出格式規定一定要有 `order_id`，信裡沒有它也會生一個。信裡又常有長得像訂單編號的數字（電話、物流單號、金額），它可能拿錯。

程式我會這樣擋，照我會先做的順序：

1. 讓它可以回「沒有」。`order_id` 允許 null，prompt 寫清楚找不到就回 null，範例也放一封沒有編號的信。
2. 回原信比對。抽出來的編號要在原信裡找得到一模一樣的，找不到就當沒抽到。這步是純程式，不花 token。
3. 查訂單系統。編號要存在，而且是這個寄件人的訂單，不是就轉人工。
4. 重試一兩次還不過就給人看，不要一直試到過。
5. 記每天幾封沒過、幾封轉人工，數字突然變高就要去看。

stock-agent 我有做過類似的。我要求模型回 JSON，程式只抓 JSON 那段解析，失敗就記 log、跳過那支股票，不讓錯的結果往下走。

## 4. 用另一個 LLM 當評審的風險與控制

這個我每天在用。我寫程式是用 Claude Code，寫完再讓另一個模型（Fable）來評分和挑毛病。換一個模型看，常常抓得到寫的那個模型自己看不到的問題，所以我覺得 LLM 當評審是有用的。我也認同評審最好換另一家的模型，不過我自己目前用的是同一家的不同模型，還沒做到這一步。

但用下來也知道它的問題：評審也是模型，一樣會錯，而且會講得很肯定。沒給它看原始資料的話，它分不出內容是不是捏造的。同一題問兩次，結論可能不一樣。如果一直照它的意見改，最後可能只是在討好評審。另外客訴信有個資，送給評審前一樣要遮罩。

我的做法：

- 評審不要跟寫的是同一個模型。能換另一家更好，至少要換一個模型。
- 原信一定要一起給它，不能只給答案。
- 它說有問題的，要回去對原始資料確認才算數，不直接照它的結論改。
- 有標準答案的部分（訂單編號、類別）先用程式比對，LLM 評審留給沒有標準答案的，例如回覆寫得好不好。
- 評分只分合格、不合格，不用 1 到 10 分。定期抽幾筆人工看，確認評審沒有走樣。
