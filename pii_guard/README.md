# pii_guard：送出前遮罩個資、回來後還原

`pii_guard` 掛在 LLM Gateway 前後。送出前，它把訊息裡的手機號碼、email、身分證字號、信用卡號換成 `[PHONE_1]` 這類代碼，對照表留在本機記憶體。模型回答後，它把代碼換回原值，再交給使用者。

模組只用 Python 標準函式庫。測試在 `tests/q3/`，執行方式如下。

```bash
uv run pytest tests/q3
```

## 如何使用

最小的用法是一段文字配一個 `Vault`。`Vault` 是一個對話的對照表。

```python
from pii_guard import Vault, mask, unmask

vault = Vault()
masked = mask("我的手機 0912-345-678，email amy@example.com", vault)
# masked == "我的手機 [PHONE_1]，email [EMAIL_1]"
unmask("已寄確認信到 [EMAIL_1]", vault)
# == "已寄確認信到 amy@example.com"
```

### 掛在 Gateway 前後

Gateway 收到 OpenAI 格式的請求後，先呼叫 `before_request`，再轉給雲端模型。模型回應後，Gateway 呼叫 `after_response`，再回給呼叫端。

```python
from pii_guard import StreamUnmasker, Vault, mask_messages, unmask

# 對照表只放在 Gateway 本機記憶體，依對話 ID 分開。對話結束就刪除，也不寫進 log。
vaults: dict[str, Vault] = {}


def before_request(conversation_id: str, body: dict) -> dict:
    vault = vaults.setdefault(conversation_id, Vault())
    return {**body, "messages": mask_messages(body["messages"], vault)}


def after_response(conversation_id: str, response: dict) -> dict:
    vault = vaults[conversation_id]
    for choice in response["choices"]:
        message = choice["message"]
        if message.get("content"):
            message["content"] = unmask(message["content"], vault)
        for call in message.get("tool_calls") or ():
            call["function"]["arguments"] = unmask(call["function"]["arguments"], vault)
    return response
```

幾個要注意的地方：

- 同一個對話要用同一個 `Vault`。同一個值在每一輪都拿到同一個代碼，模型才能前後一致地提到「[PHONE_1]」。
- `mask_messages` 會遮罩字串 content、list 形式 content 裡的 text 部分、歷史訊息裡 `tool_calls` 的參數，以及 `role: "tool"` 的工具結果。它回傳新的訊息，不改動傳入的物件。
- 模型回覆的 `tool_calls` 參數必須先還原，才能執行工具。否則工具會拿 `[PHONE_1]` 去查訂單。還原後的參數仍是合法 JSON，因為原值不含引號或反斜線。
- 圖片等非文字部分原樣保留，見「已知限制」。

串流回應用 `StreamUnmasker`，每個 chunk 呼叫一次 `feed`，結束時呼叫 `flush`。

```python
def stream_to_user(conversation_id: str, chunks):
    unmasker = StreamUnmasker(vaults[conversation_id])
    for chunk in chunks:
        yield unmasker.feed(chunk["choices"][0]["delta"].get("content") or "")
    yield unmasker.flush()
```

## 偵測規則

所有規則在偵測前先把全形英數與符號轉成半形，不斷行空白和排版用的連字號也當成一般的空白和連字號，所以「０９１２３４５６７８」也會被遮罩。代碼還原時一律換回使用者原本打的字。

| 種類 | 代碼 | 格式 | 驗證 |
| --- | --- | --- | --- |
| 手機 | `[PHONE_n]` | `09` 開頭共 10 碼，可用空白或連字號分組。也接受 `+886 9...`、`886-9...`。 | 沒有檢查碼，靠上下文排除誤判。 |
| Email | `[EMAIL_n]` | `帳號@網域.頂級網域` 的實用寫法。 | 無。 |
| 身分證字號 | `[NATIONAL_ID_n]` | 1 個英文字母，接 1 或 2，再接 8 碼。新式居留證第二碼為 8 或 9，一併處理。 | 內政部檢查碼。 |
| 信用卡號 | `[CREDIT_CARD_n]` | 13 到 19 碼連續數字，或 4-4-4-4（最後一組可以是 2 到 4 碼）、4-4-4-4-3、4-6-5、4-6-4 分組，分隔符號為空白或連字號。 | Luhn 檢查碼。部分銀聯卡沒有 Luhn 檢查碼，所以 62 開頭的號碼不檢查。 |

代碼編號規則如下：

- 同一個值永遠拿到同一個代碼。不同的值依出現順序編號，例如 `[PHONE_1]`、`[PHONE_2]`。
- 如果使用者的文字裡本來就有 `[PHONE_1]` 這個字串，`Vault` 會跳過這個編號。還原時只換 `Vault` 發出的代碼，所以使用者打的字不會被改掉。
- 模型自己編出來的代碼（例如 `[PHONE_9]`）不在對照表裡，原樣保留。

新增一種個資，只要在 `EntityKind` 加一個成員，並在 `pii_guard/detectors.py` 的 `DETECTORS` 加一列：格式、驗證函式、上下文排除規則。偵測流程不用改。`DETECTORS` 的順序就是優先順序。email 排第一，因為 email 帳號可能長得像手機號碼。

## 怎麼降低誤判

原則是用驗證排除誤判，而不是把格式寫得更嚴格或更窄。格式寫窄會漏掉真的個資。驗證只排除「確定不是」的情況。

1. **檢查碼。** 隨機的 16 碼數字只有十分之一能通過 Luhn，隨機的身分證格式字串也只有約十分之一能通過檢查碼。商品編號、金額這類數字大多在這一步被排除。
2. **邊界。** 比對結果的前後不能緊接英文字母或數字。手機的後面例外，可以接英文字（常有人寫「0912345678LINE同號」），只有接數字才不算。訂單編號 `2026110609123456780` 中間雖然有 `0912345678`，也不會被當成手機。
3. **業務編號保護清單。** 完全落在 `DEFAULT_PROTECTED` 列出的格式裡面的，不當成個資。只是有一部分重疊的照樣遮，例如 `ord-team@example.com` 還是一個 email。預設值是我的假設，上線前要換成公司實際的格式：
   - `ORD-` 或 `SKU-` 開頭的編號。
   - `YYYYMMDD` 開頭、共 12 到 19 碼的數字，例如訂單編號或 `20261106091238` 這種時間戳記。目前發行中的卡別都不以 20 開頭（Mastercard 2 系列從 2221 起），所以這條規則不會藏住真的卡號。

   這些格式，還有第 4 點用到的中文關鍵字（金額、訂單編號、電話這些詞），都放在 [`settings.json`](settings.json)，換成公司實際的寫法不用改程式。

   呼叫端也可以在呼叫時加自己的格式：

   ```python
   import re
   from pii_guard import DEFAULT_PROTECTED, mask

   protected = (*DEFAULT_PROTECTED, re.compile(r"INV-\d+"))
   mask(text, vault, protected)
   ```

4. **上下文。** 兩條規則：
   - 數字緊鄰金額標記（`$`、`NT$`、`NTD`、`TWD`、`金額`、`總計`、`合計`、`元`）時，不當成卡號。手機不看這一條：金額不會是 09 開頭，這條只會讓真的手機漏掉。
   - 連續 10 碼 `09` 開頭的數字，前面緊接 `訂單編號`、`訂單號碼`、`商品編號`、`單號`、`貨號` 時，當成業務編號。但同一段標籤裡如果也有 `電話`、`手機`、`聯絡`、`tel`、`phone`，仍然遮罩。

規則判斷不清楚時一律遮罩。下表是幾個例子，每一個都有對應的測試：

| 輸入 | 結果 | 原因 |
| --- | --- | --- |
| `訂單編號 0912345678` | 不遮罩 | 標籤緊接在數字前，而且沒有電話相關字詞。 |
| `訂單編號 0912-345-678` | 遮罩 | 訂單編號不會用手機的方式分組。 |
| `訂單聯絡電話 0912345678` | 遮罩 | 標籤是電話。 |
| `手機訂單編號 0912345678` | 遮罩 | 同時提到手機與訂單編號，判斷不清楚。 |
| `單號查好了請打給我 0912345678` | 遮罩 | `單號` 不是緊接在數字前。 |
| `卡號 4111 1111 1111 1112` | 不遮罩 | Luhn 不通過。 |
| `應付金額：4111111111111111 元` | 不遮罩 | 前後都是金額標記。 |

完整的反例在 `tests/q3/test_pii_false_positives.py`。

## 漏判與誤判哪個嚴重

漏判比較嚴重。

漏判代表客人的個資已經送到第三方的雲端模型。資料送出去就收不回來，也直接違反公司規定，還可能要依個資法通知當事人。誤判的代價是模型看到 `[PHONE_1]` 而不是原本的訂單編號，回答可能變差，或工具拿到錯的參數。誤判的值在回來時會被還原，使用者看到的文字不受影響，問題也能事後修正。

所以模組偏向召回率：格式比對寫寬，再用檢查碼、保護清單和上下文排除誤判。判斷不清楚時遮罩。

衡量方式：

- 從真實客服對話抽樣，先去識別化（把真的個資換成格式相同的假資料），再人工標出每個個資的位置與種類。
- 依種類分別算召回率（有多少個資被抓到）和精確率（被遮罩的東西有多少真的是個資）。
- 先訂召回率的門檻，在門檻內再壓低誤判。每次改規則都重跑這份資料集。
- 上線後只記錄每種代碼的數量，不記錄原值。數量突然變化時，回頭檢查規則。

## 串流的問題

模型用串流一段一段回傳時，還原會遇到以下問題：

- **代碼被切斷。** `[PHO` 在這一段，`NE_1]` 在下一段。逐段還原會漏掉。`StreamUnmasker` 會保留結尾那段「還可能變成代碼」的文字，等下一段到了再一起處理。測試涵蓋每一個切點。
- **緩衝增加延遲。** 保留的文字最多是一個代碼的長度，例如 `[CREDIT_CARD_12]` 是 16 個字元，延遲很小。工具呼叫的參數不同。JSON 參數要整段收齊才能還原與執行，不能邊收邊還原。
- **模型改寫代碼。** 模型可能把 `[PHONE_1]` 寫成 `[PHONE 1]`、`PHONE_1`，或翻譯成 `[電話_1]`。這些都還原不了。對策是在 system prompt 要求模型原樣保留方括號代碼，並統計「長得像代碼但對照表裡沒有」的次數。只記數量，不記內容。
- **只在最後一站還原。** Gateway 的 log、快取、監控都應該只看到代碼。還原放在最靠近使用者的那一步，原值就不會出現在中間的系統裡。

## 出錯或逾時要擋還是放

送出前的遮罩出錯或逾時，請求要擋下來（fail closed）。可以直接回錯誤，或改送公司內部部署的模型。原因是送出去就無法收回，而公司規定是「不得含個資」，沒有例外。被擋下的請求可以重試，外洩不能撤回。

回來後的還原出錯或逾時，不算外洩，因為個資從頭到尾沒有離開本機。這時要放行，把仍含代碼的回答交給使用者，並附上「部分資料以代碼顯示」的提示。丟掉整個回答對使用者沒有幫助。例外是工具呼叫。參數還原失敗時不能執行工具，否則 `[PHONE_1]` 會被寫進訂單系統。Gateway 重啟導致對照表遺失時，也照這個方式處理。

時間預算方面，遮罩要有明確的上限，超過就當成出錯。正規表示式本身很快。在開發機上實測，約 20 萬字元、含上萬筆個資的輸入在 40 毫秒內處理完。風險在於回溯失控（catastrophic backtracking），所以每個樣式都保持線性。數字長度有上限，email 只從一串字元的開頭開始比對，判斷重疊時也只看每個字元一次。兩個測試守住這件事。`test_email_shaped_input_without_domain_stays_linear` 用 10 萬字元的惡意輸入，`test_pasted_customer_list_stays_fast` 用 2 萬筆客戶資料。

## 已知限制

- 姓名與地址也是個資，但正規表示式抓不準。下一步是在本機跑中文 NER 模型，結果一樣交給 `Vault` 編碼。
- 連續 10 碼 09 開頭的數字前面如果是 `單號`、`訂單編號`，一律當成業務編號，就算那句話是「我沒有單號 0912345678」。同一個號碼因此可能一處被遮、一處沒被遮。
- 只處理台灣手機。市話（例如 `02-2345-6789`）和外國電話格式沒有處理，因為市話和很多業務編號長得一樣，需要更多上下文規則。
- 舊式居留證（第二碼是英文字母）沒有處理。
- 圖片與檔案原樣送出。截圖裡的個資要靠 OCR 或直接擋下。
- 同一支手機寫成 `0912345678` 和 `0912-345-678` 會拿到兩個代碼。這是為了還原時保留使用者原本的寫法。
- 使用者如果在之後的對話打出先前發過的代碼，例如 `[PHONE_1]`，模型回答裡的這個代碼會被還原成原值。這只影響顯示，不會外洩。
